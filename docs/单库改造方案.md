# exmsys 单库改造方案（v1.0 · **已实施**）

> 目标：题库与用户数据并入**单一数据库**，程序只连一个库；题库分「公共题库 / 用户自有题库」两层；
> 用户数据通过 ID 关联题目，管理员改题后所有用户自动看到新内容；为云端部署（统一数据库）打好底子。
>
> **实施状态（2026-09-24）**：已按本方案全面实施并完成数据迁移 + 验证。
> 实施过程中发现并修正了 3 处偏差，详见文末 **十一、实施结果与偏差记录**。
> 实际代码与数据结构以 `docs/需求说明书.md` / `docs/设计说明书.md`（均为 v2.5）为准。

---

## 一、本次改动要解决的问题

| 现状 | 问题 |
|---|---|
| 每个用户一个 SQLite 文件（`data/users/<user_id>.db`） | 5118 道题被物理复制 **5** 份（每份 9.3MB）；云端 PaaS 文件系统临时、多实例不共享 |
| `utils/account_manager.py::_create_user_db()` 用 `shutil.copy2(MASTER_DB, user_db)` 建号 | 建一个号就多一份 9.3MB 全量副本 |
| master 只在「建号那一刻」被使用一次 | 已有用户没有任何路径能同步 master 的改动 → **改了题库，用户库不变** |
| 题目主键由内容派生：`id = md5(题干+选项+答案)[:12]` | 改一个字，ID 就变；用户的 `question_stats` / `wrong_questions` / `answer_records`（现 17908 条）全按旧 ID 存 → 该题历史**静默断链** |
| `data_access.py::save_questions()` = `DELETE FROM questions` + 全量重插 | 每次导入都在重建整个题库；所有个人记录表分散在 5 个文件里 |
| 身份 = `md5(User-Agent + Sec-CH-UA-Platform)` | 这只是浏览器版本号，云端同版本浏览器会落到同一 user_id（串号） |
| `accounts.json` / `user_mapping.json` 是本地文件 | 多实例/重启丢失 |

## 二、本方案的拍板前提

1. **单库**：所有题目与用户数据都在 `data/exmsys.db`，程序只连这一个库。
2. **题库分两层**：
   - **公共题库**（= 初始题库）：全局唯一一份，**只有管理员可改**；
   - **用户自有题库**：用户可自行导入/清理，**只影响自己，不影响公共题库**。
3. **管理员账号**：用户名 `admin` / 密码 `admin`，系统首次启动自动创建（`role='admin'`）。
4. **管理员修题方式**：直接操作数据库修改内容，**不改 ID**。

## 三、目标架构

### 3.1 表结构总览

**A 类 · 公共内容（题库本体，含 `owner_id` 分层）**

| 表 | 主键 | 关键列 | 说明 |
|---|---|---|---|
| `questions` | `id` | `owner_id`、`source_file`、`index_num`、`type`、`question`、`options`、`answer`、`explanation`、`md5`、`category`、`exam_type`、`case_study_id`、`is_case_background` | `owner_id='__public__'` → 公共题库；`owner_id='<user_id>'` → 该用户的私有题。唯一约束由 `md5` 改为 **`UNIQUE(owner_id, md5)`** |
| `case_studies` | `id` | `title`、`background_id`、`question_count`、`exam_type`、`owner_id` | 与题库同样分层 |

> 用哨兵值 `'__public__'` 而不是 `NULL` 表示公共，是为了让 `UNIQUE(owner_id, md5)` 真正生效
> （SQLite 中 `NULL` 互不相等，会导致公共题库的去重失效）。
> 各 owner 的题目 ID 全局唯一：新增题的 ID 按 `md5(owner_id + "|" + 内容)[:12]` 生成，
> 避免「用户导入与公共题库同一个 docx」时 ID 撞车。

**B 类 · 用户数据（全部新增 `user_id`，按用户隔离）**

| 表 | 主键变化 | 说明 |
|---|---|---|
| `question_stats` | `question_id` → **`(question_id, user_id)`** | 掌握度、遗忘曲线、自评不确定 |
| `wrong_questions` | `question_id` → **`(question_id, user_id)`** | 错题本 |
| `answer_records` | `id`（不变） | 新增 `user_id` 列 + 索引 |
| `exam_records` | `id`（不变） | 新增 `user_id` 列（JSON 里无题号，无需改内容） |
| `mock_exam_records` | `id`（不变） | 新增 `user_id` 列（同上） |
| `study_records` | `session_id`（不变） | 新增 `user_id` 列 |
| `drafts` | `id`（不变） | 新增 `user_id` 列 |
| `user_config` | **`(user_id, key)`** | 由原 `config` 表拆出（每人一份设置） |
| `app_config` | `key` | 全局配置（题库版本号 `_questions_data_version` 等） |

**C 类 · 身份（替代两个 JSON 文件）**

| 表 | 主键 | 关键列 | 说明 |
|---|---|---|---|
| `users` | `user_id` | `username`（唯一，匿名用户为 NULL）、`password_hash`、`role`（`admin`/`user`）、`created_at`、`last_login` | 替代 `accounts.json` 的 `accounts` 段 |
| `user_devices` | `device_fp` | `user_id`、`first_seen`、`last_seen` | 替代 `user_mapping.json` + `accounts.json` 的 `by_device` 段 |

> `user_id` 派生算法**保持不变**（`md5("exmsys_device_" + 指纹)[:12]`），
> 这样现有用户在迁移后 user_id 不变，会话与数据不受影响。

### 3.2 用户可见题集

```
可见题 = owner_id = '__public__'   ← 公共题库，管理员改一次，全员立即生效
       + owner_id = '<当前 user_id>'  ← 用户自己导入的题
```

按 `exam_type` 的筛选逻辑完全不变。

**关键点：公共题库只有一份，用户的统计/错题只存 `question_id`，不存题目副本。
所以「初始题库修改后用户的题也跟着变」不需要任何同步机制——用户读到的就是那一条。**

### 3.3 权限矩阵

| 操作 | 管理员 | 普通用户 |
|---|---|---|
| 查看题目 / 答题 / 统计 / 错题本 | ✅ | ✅ |
| 导入题库 | 可导入到**公共题库** | 只能导入到**自己的题库** |
| 清空题库 | 清空**公共题库**（双重确认 + 影响全员警告） | 只清空**自己的题**，公共题库不受影响 |
| 清空答题记录 | ✅（自己的） | ✅（自己的） |
| 用户管理 | ✅ | ❌ |

## 六、数据迁移方案

**源**：`data/master/exmsys.db`（题库）+ `data/users/ee9dad99522c.db`（唯一在用的用户库）+ 两个 JSON
**目标**：`data/exmsys.db`（新结构）

| 步骤 | 内容 |
|---|---|
| 0 | 停 Streamlit 服务；**全量备份** `data/` → `data/backup/<时间戳>_pre_single_db/` |
| 1 | 新建 `data/exmsys.db`，建全部新表 |
| 2 | 导公共题库：master 的 `questions`(5118) / `case_studies`(6) → `owner_id='__public__'`，**ID 原样保留** |
| 3 | 导用户数据：`question_stats`(5109) / `wrong_questions`(21) / `answer_records`(17908) / `exam_records`(135) / `mock_exam_records`(30) / `study_records`(21) / `drafts`(3) → 加 `user_id='ee9dad99522c'` |
| 4 | 导配置：`config` 的全局键 → `app_config`；其余 20 项 → `user_config` |
| 5 | 导身份：`accounts.json` + `user_mapping.json` → `users` + `user_devices` |
| 6 | 创建管理员 `admin` / `admin`（`role='admin'`） |
| 7 | 丢弃 4 个空用户库（纯 master 副本，**备份先留着**），原文件归档到 `data/archive/` |
| 8 | **校验**：逐表计数比对 + 抽 20 道题比对题干/答案/解析 + 抽 3 个用户统计比对 |

**回滚**：删掉新库 → 从 `data/backup/<时间戳>_pre_single_db/` 整体还原 → 代码 `git checkout` 回滚。

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 手改题目内容后 `md5` 与内容不一致 → 再次导入时该题被当成新题重复入库 | 提供 `scripts/refresh_question_md5.py`（**保 id** 重算 md5），改题后跑一次即可 |
| `question_stats` / `wrong_questions` 改复合主键，SQLite 不能原地改 | 迁移时按新结构**重建表**再导数据，全程在副本上演练 |
| `admin/admin` 是弱密码 | 保留（按你的要求），但登录后首页常驻「建议改密」提示；**上云前必须改** |
| SQLite 单写者，多用户并发写 | 单机够用（WAL 已开）。上云换 Postgres 时只需替换 `SQLiteDataAccess` 一个类 |
| 4 个「空」用户库其实有人在用 | 迁移后备份保留 7 天再清理；迁移前把每个库的题数/数据量列出来给你过目 |
| 导入作业中途失败 | 导入走单事务；失败整体回滚，不留半份数据 |

## 八、验收标准

1. 全工程检索不到 `data/users/*.db` 的读写路径（程序只连一个库）。
2. **管理员直接在库里改一道题的题干** → 用户端刷新即看到新题干，且该题的统计/错题/历史**数量不变**（这是本次改造的核心验收点）。
3. 用户导入一份 docx → 只有自己可见；公共题库题数仍为 5118。
4. 用户「清空题库」→ 自己的题消失，公共题库完好。
5. 迁移后数据量一致：答题记录 17908 / 统计 5109 / 错题 21 / 考试 135 / 模拟考 30 / 背题 21 / 草稿 3。
6. 全项目 20 个 py 文件语法 0 错误；隔离副本上跑 AppTest 断言通过（含阳性对照）。

## 九、云端就绪

- 所有 SQL 集中在 `SQLiteDataAccess` 一个类 → 将来换 Postgres/Supabase **只改这一个类**，页面层零改动。
- 身份从「浏览器版本号」升级为**账号登录 + 设备登记表**，不再串号。
- 题库与用户数据同库按 `user_id` 隔离，天然适配云端统一数据库。
- 遗留项（本次不做）：账号密码强度与找回、多实例共享（需 Postgres）。

| 2 | 管理员改题后用户自动看到、历史不断链 | ✅ ID 原样保留（5118/5118 一一对应）；`test_multiuser.py` 第 8–11 项在行为层锁住 |

| 6 | 语法 0 错误 + AppTest 通过 | ✅ 25 个 py 文件语法通过、CRLF 纯净；AppTest 8 项通过（9 个页面全部渲染无异常） |

### 11.2 偏差一：`_assert_schema_ready()` 让全新库无法初始化（P0，已修）

**原方案没预见**：守卫被写在"建表过程中"——`question_stats` 还没创建就 `PRAGMA table_info` 它，
空库必然抛错。**云端首次部署直接起不来**，本地也只有老库能跑（老库里表已存在，恰好绕过）。

演练第一次就撞上（`RuntimeError: 数据库结构过旧`）。已改为：
`questions` 表不存在或为空列集时放行；只有"表已存在却缺列"才判为旧库。
并由 `test_multiuser.py` 第 1 项锁住。

### 11.3 偏差二：一级配对用「库中 md5 列」会大面积漏配（已改设计）

**原方案的假设**是"内容未变 → md5 相同 → 配得上"。实测发现：
`questions.md5` 有 **2417/5118 条与内容对不上**（历史遗留），
若沿用"新题算出的 md5 vs 库里陈旧 md5"，重新导入同一份题库文件时会有 2417 道题被误判为新题、
**换掉 ID、打断用户历史** —— 恰好是本方案要防的事故。

**改为**：一级信号用"**两侧都现算内容指纹**"（`_content_fp`），库里 md5 列退为兜底。
`test_multiuser.py` 第 9 项专门模拟"管理员直接改库导致 md5 陈旧"，验证仍能复用原 ID。

顺带否掉了"跑 `refresh_question_md5.py` 全量修复 md5"这条路：
库里有 **1237 组"题干+选项+答案完全相同、ID 不同"**的题（涉 2474 题），
重算会撞 `UNIQUE(owner_id, md5)`，只能跳过绝大多数，结果是半新半旧的混合状态。
该脚本已加警示说明，标注"一般不需要跑"。

### 11.4 偏差三：4 个"空"用户库被整库跳过，配置丢失（已修）

**原方案**的 `collect_user_dbs()` 按「有没有个人数据」过滤，
把 4 个"只登过记、没答过题"的用户库整库跳过。但它们各有 **20 项个人配置**
（每轮题量 / 每题组数 / 遗忘阈值 / 上次导入文件 / 题库类型 / data_source）。
其中 3 个还绑着真实设备（`814ef96e05a8` / `ee877709432a` / `946ca3bda85b`）——
等于把在用的用户配置丢回默认值，是数据丢失。

已改为「个人表为空只跳过个人数据拷贝，**配置一律迁移**」，
并把 `user_config` 的逐用户比对加进迁移脚本的自校验。

### 11.5 校验脚本的判定修正（避免误报）

`verify_single_db_migration.py` 初版有两处会误报，已修正：

- **md5**：初版断言"重算内容指纹必须等于库中 md5" → 会拿源库的既有状况去判迁移失败。
  改为断言"**目标逐字保留源库 md5**"（迁移保真度），另把陈旧条数作为**信息项**输出。
- **自增 id**：`answer_records` / `exam_records` / `mock_exam_records` 的 `id` 是
  `INTEGER PRIMARY KEY AUTOINCREMENT`，多个用户的库并入同一张表后**行号必然重编号**
  （源库本身也有空洞：`answer_records` 范围 [14669,33504] 只有 17908 行）。
  已确认全项目**没有任何代码引用这些 id**（页面与 DAO 只用 `questions.id` 与 `(question_id,user_id)`），
  故比对时排除该列。
