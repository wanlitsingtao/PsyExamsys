### 1.2 分层职责说明

| 层级 | 职责 | 禁止操作 |
|------|------|---------|
| 展示层 | 用户交互、参数收集、结果展示 | 禁止直接操作数据库 |
| 业务逻辑层 | 抽题算法、成绩计算、错题规则、缓存管理、用户上下文、身份判定 | 禁止直接写SQL |
| 数据访问层 | SQL执行、事务管理、per-rerun缓存、owner/user 隔离 | 禁止包含业务逻辑 |
| 数据存储层 | 数据持久化 | — |

**v2.5 关键设计约束（改动前必读）**

1. **唯一数据库**：全系统只有一个 `data/exmsys.db`。任何"切库"逻辑都不应再出现；
   用户隔离一律靠 SQL 条件里的 `user_id` / `owner_id`。
2. **题目 ID 一经分配永不变更**。这是"管理员改题库不切断用户历史"的基础，
   也是"用户题库与初始题库通过 ID 关联"的落地方式。任何会让 ID 漂移的改动都是缺陷。
3. **`_current_user_id` 是模块级全局变量**，Streamlit 多 session 共享进程会互相覆盖，
   因此 app.py 必须**每一帧**调用 `set_current_user()` 校正（该函数幂等，无额外开销）。
4. **作用域不能用 `<div class='wrap'>` 包裹来限定**：markdown / columns / button
   各自是独立 React 组件，那个 div 是封闭空 div，后续元素是它的兄弟节点。
   限定作用域必须用真实容器 testid（`[data-testid="stSidebar"]`、`[data-testid="stMain"]`）
   或 `st.container(key=...)` 生成的 `class="st-key-<key>"`。

## 2. 数据访问层设计（DAO）

### 2.1 单例 + 用户上下文

```python
_DAO_SINGLETON = None

def get_data_access(db_path=None, user_id=None) -> DataAccess:
    global _DAO_SINGLETON
    if _DAO_SINGLETON is None:
        _DAO_SINGLETON = SQLiteDataAccess(db_path=db_path, user_id=user_id)
    elif user_id is not None:
        _DAO_SINGLETON.set_user_id(user_id)   # 幂等同步用户上下文
    return _DAO_SINGLETON

def reset_data_access():                      # 测试或库切换时丢弃单例
    global _DAO_SINGLETON
    _DAO_SINGLETON = None
```

`SQLiteDataAccess` 内的上下文解析：

```python
def _uid(self, user_id=None):     # 生效的 user_id：显式传入优先，否则用当前上下文
    return user_id if user_id else self.user_id

def _owner(self, owner_id=None):  # 生效的 owner：显式传入优先，否则写自己的私人题库
    return owner_id if owner_id else self.user_id
```

### 2.2 连接分两级

```python
def _get_conn(self):          # 读写连接：WAL + 同步/缓存调优
    conn = sqlite3.connect(self.db_path, timeout=10)
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA journal_mode=WAL")
    conn.execute("PRAGMA synchronous=NORMAL")
    conn.execute("PRAGMA cache_size=-4000")
    return conn

def _get_light_conn(self):    # 轻量连接：不做任何 PRAGMA，仅供"每帧读一眼"的小查询
    conn = sqlite3.connect(self.db_path, timeout=10)
    conn.row_factory = sqlite3.Row
    return conn
```

**为什么要分两级**：`PRAGMA journal_mode=WAL` 需要取写锁，代价远高于一次普通 SELECT。
改造前 `get_questions_version()` 每帧都走 `_get_conn()`，实测约 **259ms/次**，
是当时"勾选答案卡顿"的头号元凶。现在该函数走 `_get_light_conn()`。

### 2.3 建表与旧库守卫

`_init_db()` 在 DAO 首次初始化时执行：

1. 创建 `questions` / `case_studies`（带 `owner_id`）
2. **调用 `_assert_schema_ready()` 做旧库守卫**
3. 创建唯一索引 `uniq_questions_owner_md5(owner_id, md5)`
4. 创建 7 张用户数据表（带 `user_id`）、`app_config` / `user_config`、`users` / `user_devices`
5. 确保题库版本号记录存在（`app_config._questions_data_version`）

**旧库守卫的规则（曾经写错过，必须保持）**：

```python
def _assert_schema_ready(cur):
```

### 2.5 per-rerun 缓存

`_rerun_cache_questions` / `_rerun_cache_stats` 缓存本次 rerun 内的查询结果。
每个缓存都记录其归属的 `user_id`（`*_user`），读取时校验一致才复用 ——
因为这些是模块级全局变量，多 session 会互相覆盖，不校验就会串号读到别人的数据。
每次 rerun 开始时由 `invalidate_rerun_cache()` 清空。

## 3. 核心业务算法设计

### 3.1 优先级抽题算法

**目标**：让用户优先看到最薄弱的题目。

**四层排序**（关联系数计算后用 `_priority_sample` 执行）：

| 排序键 | 说明 |
|---------|------|
| `wrong_count - correct_count` 降序 | 答错多于答对的题优先 |
| 答错过(0) > 从未答过(1) > 答对过(2) | 副排序 |
| `wrong_count` 降序 | 同层级内高频错题优先 |
| 随机 | 最终平局打破 |

### 3.2 均衡采样算法

**目标**：确保超类下各子板块均匀出题，避免大板块垄断。

**算法步骤**（`_balanced_sample_by_type`）：
1. 计算基础配额：`base = total // n`
2. 前 `extra` 个类别多分1道（`extra = total % n`）
3. 各子板块内部按优先级排序后取前 N 道
4. 配额未用完时从剩余题目中按优先级补齐

### 3.3 掌握度计算算法

**目标**：基于历史答题记录，计算每道题的掌握度等级（0-5级）。

**输入**：该题所有历史答题记录（answer_records 表）

**计算步骤**（`_recalc_mastery_fields`）：
1. 统计 `correct_count`、`wrong_count`
2. 计算正确率 `accuracy = correct_count / (correct_count + wrong_count)`
3. 映射正确率到掌握度等级：

| 正确率范围 | 等级 | 说明 |
|-----------|------|------|
| < 20% | 0级 | 未掌握 |
| 20%-40% | 1级 | 薄弱 |
| 40%-60% | 2级 | 入门 |
| 60%-80% | 3级 | 良好 |
| 80%-95% | 4级 | 熟练 |
| ≥ 95% | 5级 | 精通 |

4. 计算置信度：答题次数越多置信度越高（`confidence = min(1.0, (correct_count + wrong_count) / 10)`）
5. 检测不稳定标记：
   - **消退型**：近期正确率明显低于远期 → `unstable = 1, retention_due = 计算值`
   - **波动型**：正确/答错交替出现 → `unstable = 1`

### 3.4 错题入出本规则

**入本条件**（满足以下所有条件）：
- `wrong_count >= correct_count`
- `wrong_count > 0` 或 `correct_count > 0`（至少答过一次）

**出本条件**（满足以下任一条件）：
- `correct_count > wrong_count`（答对次数严格大于答错次数）
- 用户手动点击"我已掌握本题"且 `correct_count > wrong_count`

## 4. 缓存与性能设计

### 4.1 三级缓存体系

| 缓存层级 | 存储位置 | 失效时机 | 用途 |
|----------|----------|---------|------|
| per-rerun缓存 | `data_access.py` 模块级字典 | 每次 rerun 开始（`invalidate_rerun_cache()`） | 避免同次 rerun 多次查询 DAO |
| session_state缓存 | `st.session_state._stats_cache` 等 | `_data_version` 变化时 | 避免跨 rerun 重复读取数据库 |
| 版本号失效 | `st.session_state._data_version` | 每次数据写入后 `+1` | 触发 session_state 缓存失效 |

### 4.2 批量I/O设计

**优化前**（v2.1及之前）：每题依次调用 `add_wrong_record` / `add_correct_record` / `add_answer_record`，每次调用执行一次数据库读写。

**优化后**（v2.2及之后）：
1. 提交时先收集所有操作数据（wrong_qids / correct_qids / stats_updates / answer_records）
2. 调用 `batch_update_wrong_and_stats()` 一次性更新错题库和答题统计（1次事务）
3. 调用 `batch_add_answer_records()` 一次性追加答题记录（1次事务）

**效果**：250题提交从 ~500+ 次 I/O 降至 ~4 次 I/O，性能提升近百倍。

### 4.3 首页统计缓存

`statistics.py` 中的 `_get_cached_stats()` 函数：
1. 检查缓存版本号是否等于 `_data_version`
2. 命中：直接返回缓存数据（0次 I/O）
3. 未命中：从数据库加载6类数据，存入缓存（6次 I/O）

### 5.3 题目 ID 分配与导入配对（本题库最关键的两段逻辑）

**ID 分配**（`make_question_id`）：

```python
def make_question_id(owner_id, q) -> str:
    return md5(f"{owner_id}|{题干}{str(sorted(选项.items()))}{答案}")[:12]
```

- 把 `owner_id` 纳入哈希 → "用户私题"与"公共题"即使内容相同也得到不同 ID，互不干扰；
- 插入前若 ID 已存在，再加盐重算，保证不覆盖既有题；
- **ID 一经分配永不变更** —— 这是用户历史零断链的前提。

**内容指纹**（`question_md5` / `_content_fp`）：

```python
md5(题干 + str(sorted(选项.items())) + 答案)
```

必须**两侧现算**（新题算一次、库中行也算一次），不能拿"新题算出的值"去比
"库里存的 `md5` 列" —— 因为管理员直接改库改内容后该列不会同步，本题库里就有
**2417/5118 条**是这样的历史遗留。拿它当主键会大面积漏配，导致重新导入时给旧题换新 ID、
把用户历史打断（这正是本设计要防的事故）。

**三级配对**（`_match_questions`）：

| 级别 | 信号 | 适用 |
|------|------|------|
| 1 | 内容指纹（两侧现算）相同；退回库中 `md5` 列 | 内容未变 |
| 2 | `(source_file, index_num, type)` 相同 | 题号可靠时 |
| 3 | 同一 `source_file` 内题干文本相似度最高且 ≥ 0.60 | 题干被改过 |

- 级别 2 **不能单独依赖**：本题库中 `(source_file, index_num)` 并不唯一
  （曾有文件 500 题里 250 题 `index_num=0`；另一文件 220 题全部 #0；99 题 `source_file` 为 NULL）
- 级别 3 是 `O(n·m)` 比较，设 **20 万次比较预算** + `real_quick_ratio()` / `quick_ratio()` 预筛；
  超预算就停止模糊配对、剩余按新题插入（宁可多几道新题，也不让导入卡死）
- `used_ids`（只增不减，防新题 ID 撞车）与 `matched_ids`（`replace` 模式据此判定删除）**是两个独立集合**，
  混用会导致 `replace` 永远删不掉东西

**md5 唯一索引的防撞保护**：更新已匹配题时，若新 `md5` 已被同 owner 的另一题占用
（本题库有 1237 组内容重复的题），则**保留本行原 md5** 并记入导入日志，
绝不触发 `UNIQUE(owner_id, md5)` 冲突。

- 两科独立计时、独立提交
- 支持草稿保存与恢复

**巩固练习（consolidation.py）**：

```
idle ──► running ──► submitted
```

- 与专项训练类似，但题目来源为"不稳固题目"
- **题数可配**（2026-09-30）：读配置 `consol_per_round`（默认 60，范围 10~200），
  `count = min(len(combined), consol_per_round)`；题池不足时按实际数量出题。

### 6.3 响应式布局断点（v2.9.4）

界面样式集中在两处：`app.py` 的主样式块（导航/卡片/按钮/侧边栏）与
`utils/answer_card.py` 的 `CARD_CSS`（答题卡网格与右栏）。断点只有三档：

| 断点 | 目标设备 | 关键规则 |
|------|---------|---------|
| `≤1200px` | 小笔记本 | `.block-container` 收为 `92vw` |
| `≤900px` | 平板竖屏 / 大屏手机 | 内容区 100% 宽；答题卡右栏**回落整宽并取消粘性**（`answer_card.py`），题目区与答题卡改为上下排 |

**🩸 断点阈值不可混用的原因（2026-10-10 实测踩坑）**：
「侧边栏展开态占满全宽」这条规则**必须放在 `≤640px`**，不能放在 `≤900px`。
iPad 竖屏的 CSS 视口宽度是 768 / 810 / 820 / 834px，会命中 900px 断点；
而 iPad Safari 从 iOS 13 起上报**桌面级 UA**（`Macintosh; Intel Mac OS X`），
Streamlit 因此判定它**不是移动端、不会自动收起侧边栏**，配合
`initial_sidebar_state="expanded"` → 侧边栏占满 100% 宽、**主内容区被挤成 0 宽**
（实测 768×1024 下 `sidebarWidth=768` / `mainWidth=0`），用户打开就是满屏左侧栏。
收到 640px 后：iPad 竖屏恢复原生 300px 窄栏 + 主内容 468px 并排，手机与 PC 行为不变。

#### 6.3.1 侧边栏默认行为：`initial_sidebar_state="auto"`（v2.9.4）

|---|---|

## 7. 草稿系统设计

### 7.1 草稿数据结构

### 7.2 草稿保存与恢复流程

**保存**：
1. 用户在答题过程中点击"保存草稿"

3. 调用 `save_draft(draft_type, data)` 写入 `drafts` 表

1. 开始界面加载该 `draft_type` 的所有草稿
2. 用户点击"继续作答"
3. 从 `drafts` 表读取草稿数据
4. 恢复 `question_ids`、`answers`、当前进度
5. 进入 `running` 状态继续答题

**模式识别（`utils/data_access.get_db_mode()`）**

| 优先级 | 条件 | 结果 |
|---|---|---|
| 1 | `EXMSYS_DB_MODE` = `sqlite` / `supabase` | 强制指定 |
| 2 | 设了 `EXMSYS_DATA_DIR` | **强制 sqlite**（安全阀，见下） |
| 3 | 能取到 Postgres 连接串 | `supabase` |
| 4 | 兜底 | `sqlite` |

连接串来源（`detect_pg_dsn()`，一份配置全场景通用）：
环境变量 `EXMSYS_DB_URL`/`SUPABASE_DB_URL`/`DATABASE_URL` → `st.secrets`
→ 直接解析 `.streamlit/secrets.toml`（非 Streamlit 场合）→ 项目根 `.env`。

> **第 2 条是安全阀，不可删。** 自动化测试把 `EXMSYS_DATA_DIR` 指向真实库的临时副本，
> 若开发机环境里恰好存在 `SUPABASE_DB_URL`，没有这条会把测试数据写进云端生产库。
> `scripts/_testenv.py` 另设 `EXMSYS_DB_MODE=sqlite` 作双保险。

**为什么是「方言翻译层」而不是「另写一套 PG SQL」**

项目有 129 条业务 SQL、109 个 `?` 占位符，全部集中在 `SQLiteDataAccess`。
手抄一套 Postgres 版的风险是：一次性抄写极易漏列/错列（**静默数据损坏**），
且此后每改一个功能都要改两处、必然漂移。因此采用继承 + 运行时翻译：

```
PostgresDataAccess(SQLiteDataAccess)   ← 全部业务方法继承，SQL 一个字不改
    仅覆盖 5 个存储引擎相关方法：
      __init__ / _get_conn / _get_light_conn / _init_db / _assert_schema_ready
    PgCursor.execute() 负责把 SQLite 方言翻成 Postgres 方言
```

翻译规则仅 4 条：

| SQLite | Postgres |
|---|---|
| `?` | `%s` |
| `INSERT OR REPLACE INTO t (cols) …` | `INSERT INTO t (cols) … ON CONFLICT (PK) DO UPDATE SET c = EXCLUDED.c, …` |
| `INSERT OR IGNORE INTO t …` | `INSERT INTO t … ON CONFLICT DO NOTHING` |
| `PRAGMA …` / `sqlite_master` | 映射到 `information_schema`；`journal_mode` 等客户端调优语句直接吞掉 |

⚠️ **唯一需要留意的语义差异**：SQLite 的 `INSERT OR REPLACE` 是「先删后插」，
未列出的列会重置为默认值；Postgres 的 `DO UPDATE` 是「更新」，未列出的列保持原值。
本项目 8 处 REPLACE **全部列出了该表全部列**，故两种语义完全等价；
`scripts/test_pg_dialect.py` 有断言守住这个前提（少写一列即测试失败）。

**连接管理**：`PgPool` = `ThreadedConnectionPool(1, 15)`，上限可用 `EXMSYS_DB_POOL_MAX` 调小。
池是**惰性扩容**的（只有真并发才会占到上限），按 `(DSN, schema)` 分池。
空闲超 60 秒的连接在取出时探活一次（云库会掐空闲 TCP），
归还前强制 `rollback`（避免带着未结束事务的连接回池）。

**目标 schema（同一实例跑多个应用）**

一台托管 PostgreSQL（一个 Supabase 项目 = 一个实例）里可以建多个 schema，各应用各占一个，
互不干扰。本项目使用独立 schema **`psych_exm`**（兜底值 `public`，保证未配置时行为与改造前一致）。

| 位置 | 做法 |
|---|---|
| 配置读取 | `utils/data_access.detect_pg_schema()`：环境变量 `EXMSYS_DB_SCHEMA` / `DB_SCHEMA` → `st.secrets` → 直接解析 `.streamlit/secrets.toml` 的 `[supabase] schema` → `.env` → 兜底 `public`；名字走 `^[A-Za-z_][A-Za-z0-9_]{0,62}$` **白名单**，非法值直接抛错（不做转义、不尽力猜） |
| 连接建立 | `PgPool` 在每条物理连接建立后执行一次 `SET search_path TO "<schema>"`，**只放目标 schema、不放 `public`** —— 表名写错会立刻报错，而不是静默读到 `public` 里另一个应用的同名表 |
| 元数据查询 | `PRAGMA table_info` / `sqlite_master` 两条翻译 SQL 由写死 `'public'` 改为参数化传 schema |
| 启动自检 | `_init_db()` 按配置 schema 查 `information_schema.tables` / `pg_indexes`；schema 不存在时给出「整段执行 `01_schema.sql`」的明确指引 |
| 建表脚本 | `01_schema.sql` 第 0 节 `create schema if not exists` + `set search_path`，**紧跟一个断言块**：`current_schema() <> 'psych_exm'` 即 `raise exception` 中止 |
| 导入脚本 | 全程使用 `"schema"."table"` 全限定名（不依赖会话级 SET），并先校验 schema 是否存在 |

⚠️ `SET search_path` 是**会话级**的，因此连接池必须用 Session pooler（`:5432`）；
`:6543` 的 transaction pooler 不支持会话级 SET。建表脚本与导入脚本各自独立处理
（前者靠脚本内 `set search_path` + 断言，后者靠全限定名），**互不依赖**。

⚠️ 断言块是必需的：建表脚本第 1~8 节全部用裸表名，逐条选中执行会丢失 `search_path`
→ 13 张表被静默建到 `public`，污染同实例上的另一个应用。
设计取向是「**宁可报错，绝不静默建错地方**」。

**表结构不在应用内创建**：Postgres 建表需一并处理唯一索引、identity 序列、RLS 等配置，
散在启动路径里不可审计；集中在 `deploy/supabase/01_schema.sql`，
可复核、可幂等重跑。应用启动时只做**结构自检**（目标 schema 存在 + 13 张表齐全 +
`uniq_questions_owner_md5` 存在），缺则报错并给出修复指引。

**安全**：不使用 Supabase REST/Data API（走直连 SQL）。
独立 schema **默认不在 Supabase 的 `Exposed schemas` 列表里**（默认只有 `public` / `graphql_public`），
因此 Data API / anon key 根本触不到 —— 比 RLS 兜底更硬。
在此之上仍做纵深防御：建表脚本对所有表 `enable row level security` 且**不建任何策略**，
并**在 `anon` / `authenticated` 角色存在时**才 `revoke all`（表级 + 序列级 + schema 级，共 3 处）——
应用连接的 Owner 角色默认绕过 RLS，读写不受影响。
（角色存在性判断是跨平台必需：Neon / Aiven 没有这两个角色，无条件 REVOKE 会中断整个脚本。）

**多平台兼容（Supabase / Neon / Aiven，实现侧零差别）**

三家都是标准 PostgreSQL，差异只在「连接串写法」与「两个 Supabase 专属动作」上：

| 差异点 | Supabase | Neon | Aiven |
|---|---|---|---|
| 运行时端点 | Session pooler `aws-0-<区域>.pooler.supabase.com:5432`（直连地址 **IPv6-only**，家用宽带连不上） | `ep-xxx-pooler.<区域>.aws.neon.tech`（PgBouncer **transaction 模式**） | `pg-xxx.a.aivencloud.com:<非标准端口>` |
| 建表/导入端点 | 同上 | **必须用直连** `ep-xxx.<区域>.aws.neon.tech`（transaction 模式不支持会话级特性） | 同上 |
| 用户名 | `postgres.<项目ref>`（带后缀） | 随机生成，**不是** `postgres` | `avnadmin` |
| 默认库名 | `postgres` | `neondb` | `defaultdb` |
| TLS | 强制 | 强制（连接串带 `?sslmode=require`） | 强制 |
| 空闲行为 | 7 天无活动 → 暂停，**需手动 Restore** | 5 分钟挂起计算，**下次连接自动唤醒**（~1 秒冷启动） | 长期闲置 → 关机，需手动开机 |

因此需要的改动只有两处，且**改完在 Supabase 上依然正确**（属兼容性改法，非二选一）：

1. `01_schema.sql` §6 的 REVOKE 加 `pg_roles` 存在性判断（原先无条件 REVOKE 会在
   Neon / Aiven 上抛 `role "anon" does not exist` 并**中断脚本** —— 后果是
   「表建好了、序列没对齐」，应用第一次写入才报主键冲突，属最难查的一类故障）；
2. `preflight.py` / 导入脚本的识别与提示改为按主机名分流，并补 `sslmode` 缺失告警。

验证方式：`scripts/test_cloud_schema_platform.py`（**24 项**，纯静态）——
其中最关键的一条是断言 **`from anon, authenticated` 不得出现在 `do $$` 块之外的任何位置**，
把「有人把裸 REVOKE 加回来」这种回归直接挡在提交前；
另有整套 schema 隔离断言（`create schema` / `set search_path` / 断言块存在 /
可执行代码 0 处 `public.` 前缀 / REVOKE 用 `current_schema()` 限定）。

**同一实例跑多个应用（schema 隔离）也归入这一节**：它是「复用现有实例」的部署方案，
与平台选型正交 —— Supabase / Neon / Aiven 都适用（Supabase 免费版限 2 个活跃项目，
复用实例可避免开新项目）。实现要点见上面「目标 schema」小节。

> 兼容性已核对：`_looks_like_dsn()` 只校验 `postgres://` / `postgresql://` 前缀，
> 带 `?sslmode=require` 完全兼容；`mask_dsn()` 会截断 `?` 之后，日志不泄露密码；
> 业务 SQL 无 `COPY`，运行时走 transaction 模式连接池无碍。
